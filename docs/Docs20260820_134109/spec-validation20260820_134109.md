## 6. Observações (não bloqueantes)

Registradas para transparência; nenhuma constitui `[MISS]` ou `[CONFLICT]` pelos critérios de validação:

1. **Contagens aproximadas herdadas**: o PRD refere "~90 apiExpectations" e o preâmbulo do schema da SPEC refere "~90 entidades de dataRequirements"; as contagens literais no contrato são **111 apiExpectations** e **75 dataRequirements**. A SPEC 3.2 já documenta o valor exato de apiExpectations; a menção "~90 entidades" é aproximação sem efeito prático, pois a cobertura foi verificada id a id.
2. **Domínio `clientes` (13º grupo de Edge Functions)**: o PRD lista 12 grupos; a SPEC adiciona `clientes` para abrigar os endpoints de contratos presentes no contrato. É refinamento de organização interna de backend, documentado e justificado na própria SPEC, sem criar endpoint fora do catálogo travado.
3. **Estados destacados vs inventário completo**: a lista de estados por tela na SPEC 4.5 é declaradamente "não exaustiva" (ex.: em `plano`, os estados `semana`, `read-only`, `reaproveitamento-de-estoque`, `sem-material`, `sem-plano` e `prazo-em-risco` — este distinto de `conclusao-apos-o-prazo` — não aparecem no destaque; `dashboard`, `ged` e `orcamento` aparecem apenas nos padrões transversais). A cláusula de delegação obrigatória cobre a implementação; o Coder deve tratar `screens[].states` do contrato como checklist literal, como a SPEC determina.
4. **Tabela `normas_tecnicas`**: mantida no schema para atender RF-07/RF-08 mesmo com a tela dedicada removida pelo design lock (delta-054). Não há conflito — é backend sem UI própria, coerente com a decisão travada e com o risco registrado na seção 8 do PRD.
