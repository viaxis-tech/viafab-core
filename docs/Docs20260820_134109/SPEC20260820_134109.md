## 1. Resumo do Produto

**Problema**: fábricas de sinalização viária (placas de advertência, regulamentação, indicativas e marcadores conforme nomenclatura CONTRAN) operam hoje com processos manuais e planilhas paralelas para configuração técnica de produto, explosão de BOM, geração de roteiro, planejamento de produção, controle de estoque, apontamento de chão de fábrica, qualidade, expedição e rastreabilidade — gerando retrabalho, perda de rastreabilidade e falta de visibilidade gerencial.

**Público-alvo**: PCP (Planejamento e Controle de Produção), engenheiros de produto/processo, almoxarifes, operadores de produção (chão de fábrica, tablet/celular), responsáveis por qualidade e expedição, administradores de empresa (tenant) e direção/gestão.

**Pitch**: o ViaFab é um ERP verticalizado para fábricas de sinalização viária, cobrindo o ciclo completo — configuração técnica do produto, explosão de BOM, geração de roteiro de fabricação, planejamento de produção (PCP), reserva e movimentação de estoque, execução no chão de fábrica com apontamento de tempo e consumo, controle de qualidade, expedição, rastreabilidade/auditoria e segurança multiempresa (multi-tenant) — com isolamento de dados por empresa e por unidade fabril.

**Stack escolhida**: TypeScript, PostgreSQL/Supabase (Auth + RLS + Storage), Edge Functions em Deno, GitHub Actions (CI), Vitest (testes unitários de domínio), Playwright (E2E).

**Plataforma**: Web responsiva, densidade de interface "dense", sidebar fixa de 230px. Telas de PCP/engenharia/gestão otimizadas para desktop; telas de chão de fábrica, qualidade e expedição responsivas para tablet/celular, com suporte a operação offline com fila de sincronização.

### 2.2 RLS Policies

Padrão fail-closed em todas as tabelas de negócio (RNF-03/US-26):

```sql
-- Exemplo padrão aplicado a toda tabela com tenant_id
alter table ordens_producao enable row level security;

create policy tenant_isolation_select on ordens_producao
  for select using (
    tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid
  );

create policy tenant_isolation_write on ordens_producao
  for insert with check (
    tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid
  );

create policy tenant_isolation_update on ordens_producao
  for update using (
    tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid
  ) with check (
    tenant_id = (auth.jwt() -> 'app_metadata' ->> 'tenant_id')::uuid
  );

-- Segundo nível: isolamento por unidade (delta-076/077)
create policy unidade_isolation_select on ordens_producao
  for select using (
    unidade_id = any (
      (auth.jwt() -> 'app_metadata' -> 'unidades_autorizadas')::uuid[]
    )
  );
```

- Claims (`tenant_id`, `perfil_id`, `unidades_autorizadas`) residem em `raw_app_meta_data` (nunca `user_metadata`, que é editável pelo próprio usuário).
- Nenhuma tabela tem policy `using (true)`. Ausência de policy = acesso negado (fail-closed).
- `auditoria` e `eventos_ordem`: apenas `INSERT` liberado por policy; `UPDATE`/`DELETE` sem policy correspondente (bloqueados mesmo para `service_role` via `REVOKE`).
- `snapshots`: apenas `INSERT`/`SELECT`; sem policy de `UPDATE`/`DELETE` (RNF-13).
- Tabelas de catálogo versionado (`familias_construtivas`, `normas_tecnicas`, `fichas_tecnicas`): `UPDATE` restrito a campos de metadados (ex. `ativo`); nova versão sempre via `INSERT`.
- Isolamento validado por testes automatizados (RF-37/US-26): suíte pgTAP com dois tenants fictícios tentando cross-read.

### 2.3 Triggers

- `trg_auditoria_generica`: trigger genérica `AFTER INSERT OR UPDATE OR DELETE` em tabelas críticas (ordens_producao, apontamentos, consumos, perdas, inspecoes, movimentos_estoque, familias_construtivas, normas_tecnicas, perfis) que grava em `auditoria` (captura omissões de auditoria explícita — RF-35/RNF-06).
- `trg_saldo_estoque_movimento`: `AFTER INSERT` em `movimentos_estoque` atualiza `saldo_estoque.fisico` com `SELECT ... FOR UPDATE` (concorrência segura).
- `trg_reserva_saldo`: `AFTER INSERT` em `reservas` incrementa `saldo_estoque.reservado`; ao liberar reserva, decrementa.
- `trg_apontamento_tempo`: `BEFORE UPDATE` em `apontamentos` calcula `tempo_min` quando `fim` é preenchido.
- `trg_estorno_expira`: job/trigger que invalida `estornos_apontamento` após 10 minutos (compensating transaction, nunca DELETE do apontamento original).
- `trg_baixa_automatica_consumo`: `AFTER INSERT` em `consumos` gera `movimentos_estoque` tipo `baixa` automaticamente (delta-015), respeitando `parametros_sistema.baixa_automatica`.
- `trg_ordem_status_material`: `AFTER INSERT/UPDATE` em `reservas`/`saldo_estoque` recalcula `ordens_producao.status` para `aguardando_material` quando saldo insuficiente (RF-17).
- `trg_bloqueio_qualidade`: `BEFORE UPDATE` em `ordens_producao` impede transição para status elegível a expedição quando há `inspecoes.resultado = 'reprovado' AND critica = true` sem reversão (RF-27).
- `trg_versao_familia`/`trg_versao_norma`: `BEFORE INSERT` calcula próximo `versao` e impede `UPDATE`/`DELETE` de versões existentes.

### 3.3 Middleware

- **auth-guard**: valida JWT Supabase em toda requisição; rejeita sem `tenant_id`/`perfil_id` em `raw_app_meta_data`.
- **tenant-guard**: injeta `tenant_id` do JWT em toda query; nunca aceita `tenant_id` vindo do payload do cliente.
- **unidade-guard**: valida que `unidade_id` do payload/query está em `unidades_autorizadas` do usuário.
- **rbac-guard**: consulta matriz de permissões do `perfil_id` para o módulo/ação (`GET`/`POST`/`PATCH`) antes de delegar ao use-case; nega com `403` (nunca client-side apenas — mitiga risco delta-005/101).
- **idempotency-guard**: em endpoints offline-first (apontamentos, consumos, movimentos, `POST /estoque/movimentos/sincronizar` — `api-sincronizar`), calcula chave `(tenant_id, client_generated_id)`; requisição repetida retorna o resultado já processado sem duplicar.
- **audit-writer**: pós-processamento que grava em `auditoria` para eventos sem trigger genérica aplicável (ex.: login, alteração de permissão de perfil). Inclui obrigatoriamente toda chamada a `POST /relatorios/exportar` (`api-relatorio-exportar`) e `POST /relatorios/composicoes` (`api-relatorio-salvar`) — ação `relatorio_exportado`/`relatorio_composicao_salva`, com `usuario_id`, `tipo`, `filtros` e `formato` — exigência do design lock de registrar toda exportação em auditoria.
- **validation (zod)**: valida `requestShape` de cada endpoint contra o schema espelhado do `apiExpectations`; erros retornam mensagem objetiva (RNF-09), nunca genérica.
- **error-handler**: padroniza formato de erro, nunca expõe qual campo de login está incorreto (RNF-04).

### 3.4 Agent Graph

Não aplicável. O ViaFab não possui funcionalidade de agente de IA/LLM no escopo do design lock; toda lógica de backend é determinística (regras de negócio, cálculo de BOM/roteiro, RBAC, auditoria).

### 3.5 Integrações Externas

- **Supabase Auth**: login por credenciais (email/senha), sessão JWT, claims customizadas via `raw_app_meta_data` (tenant_id, perfil_id, unidades_autorizadas).
- **Supabase Storage**: bucket-per-purpose (`documentos-ged`, `arquivos-vfb`, `etiquetas`) com isolamento por caminho (`{tenant_id}/{unidade_id}/...`) e políticas de Storage próprias — não bucket-per-tenant.
- **ViaSign** (simulado): endpoint `POST /viasign/manifesto` valida payload contra schema `viaxis.vfb/1` (zod) e persiste em `vfb_manifestos`; autenticação/assinatura/hash real do ViaSign fora do escopo desta fase (delta-023/067-075 — decisão pendente, tratada como simulação).
- **GitHub Actions**: pipeline de CI executando lint, Vitest (domain), migrations dry-run, Playwright (E2E) contra ambiente Supabase local/branch.

2. 3. `entityId` inexistente ou não autorizado (RBAC/tenant/unidade) resulta na tela `acesso-negado` ou em estado `empty`/`error` da própria tela de detalhe, nunca em erro não tratado.

## 5. Security

### 5.1 Auth Flow Completo

1. Usuário acessa `#login` e envia credenciais (`POST /auth/login`).
2. Supabase Auth valida credenciais; falha não indica qual campo está incorreto (RNF-04) — mensagem genérica "credenciais inválidas".
3. Login bem-sucedido retorna JWT com claims customizadas em `raw_app_meta_data`: `tenant_id`, `perfil_id`, `unidades_autorizadas` (array de `unidade_id`). Essas claims são setadas exclusivamente por processo server-side (Edge Function/trigger de signup), nunca editáveis pelo usuário via `user_metadata`.
4. Frontend armazena sessão via Supabase client; sidebar (`cmp-sidebar-nav`) e ações de tela são renderizadas conforme matriz de permissões do `perfil_id` obtida em `GET /auth/perfis` — ocultação client-side é apenas cosmética (RF-39), nunca a única barreira (mitigação do risco delta-005/101).
5. Toda requisição a Edge Function passa por `auth-guard` (valida JWT) → `tenant-guard` (injeta `tenant_id`) → `unidade-guard` (valida `unidade_id` do payload contra `unidades_autorizadas`) → `rbac-guard` (valida permissão do `perfil_id` para o módulo/ação) antes de qualquer acesso a dado.
6. Toda query Postgres, mesmo com `service_role` em Edge Function, respeita RLS explícita por tabela (fail-closed) — não há bypass de RLS mesmo em código server-side, exceto para o `audit-writer` explicitamente instrumentado.
7. Sessão expira por inatividade (RNF-04); expiração força novo login. Rota protegida acessada sem sessão válida redireciona para `#login`; acessada sem permissão de perfil redireciona para `#acesso-negado`.
8. Troca de unidade fabril (multi-unidade) é feita dentro da sessão ativa, revalidando `unidade_id` contra `unidades_autorizadas` a cada requisição (não requer novo login).

### 5.2 Checklist de Segurança

- [ ] RLS habilitada e fail-closed em 100% das tabelas de negócio (nenhuma tabela com policy `using (true)`).
- [ ] Claims de tenant/perfil/unidade apenas em `raw_app_meta_data`, nunca em `user_metadata`.
- [ ] RBAC aplicado no backend (Edge Functions), não apenas ocultado na UI.
- [ ] Testes automatizados de isolamento cross-tenant (US-26/RF-37) na suíte de CI.
- [ ] Tabelas `auditoria` e `eventos_ordem` append-only (sem policy de `UPDATE`/`DELETE`, inclusive para `service_role`).
- [ ] Tabela `snapshots` imutável após criação (RNF-13) — correções via `snapshot_revisao_de_id`, nunca `UPDATE`.
- [ ] Idempotência via `(tenant_id, client_generated_id)` em todos os endpoints offline-first (apontamentos, consumos, movimentos de estoque).
- [ ] Nenhuma confirmação silenciosa de movimento crítico em modo offline (RNF-11/RNF-12) — estado `pendente`/`conflito` explícito até sincronização.
- [ ] Reversão de apontamento apenas via contrapartida (`estornos_apontamento`) em até 10 minutos — nunca `DELETE` do registro original.
- [ ] Mensagens de erro de autenticação genéricas (não revelam qual campo está incorreto).
- [ ] Mensagens de erro de validação de negócio específicas e objetivas (RNF-09) — sem mensagens genéricas.
- [ ] Storage: políticas por caminho (`{tenant_id}/{unidade_id}/...`), bucket-per-purpose, nunca acesso público a documentos GED/vfb.
- [ ] Reabertura de ordem expedida bloqueada por padrão, exige permissão explícita de perfil (RF-33).
- [ ] Toda exportação de relatório (`POST /relatorios/exportar`) e salvamento de composição (`POST /relatorios/composicoes`) gera registro em `auditoria` (ação `relatorio_exportado`/`relatorio_composicao_salva`, com `usuario_id`, `tipo`, `filtros`, `formato`) — exigência do design lock.
- [ ] LGPD: minimização de coleta de dados pessoais de cliente/usuário; acesso a dado pessoal restrito por perfil (RNF-05).
- [ ] Segredos (chaves Supabase service_role, chaves ViaSign simuladas) apenas em variáveis de ambiente de servidor, nunca no bundle do frontend.
